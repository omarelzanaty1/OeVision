# Project Builder – ما يلزم في قاعدة البيانات

> الحالة: **لم تُطبَّق** على قاعدة البيانات. ملف الـ migration جاهز للمراجعة فقط:
> `supabase/migrations/20261116_project_builder.sql`

## لماذا نحتاج تغييرًا؟
جدول `projects` لا يحتوي على مكان لحفظ ترتيب المحتوى (صور/نص/شبكة/فيديو/فاصل)، ولا الوسوم، ولا مجال العمل، ولا اسم العميل، ولا تاريخ المشروع، ولا ضبط الغلاف، ولا الرابط المختصر.

## ما يضيفه (إضافات فقط، لا حذف ولا تعديل لأعمدة موجودة)
| العمود | النوع | الغرض |
|---|---|---|
| content_blocks | jsonb (افتراضي `[]`) | بلوكات المحتوى بالترتيب |
| tags | text[] | الوسوم |
| creative_field | text | المجال الإبداعي |
| client_name | text | اسم العميل |
| project_date | date | تاريخ المشروع |
| cover_focus | jsonb `{x,y,zoom}` | ضبط الغلاف دون قص الأصل |
| slug | text | رابط مختصر (فهرس فريد جزئي) |

مع قيود حجم/نوع (≤300 بلوك، ≤500KB، ≤30 وسم، …). لا تغييرات في السياسات (RLS) ولا الصلاحيات: `projects` تسمح أصلًا للأدمن فقط بالكتابة وللزوار بقراءة المنشور فقط.

## التوافق
- `gallery_images` يبقى كنسخة مرآة (أول 40 صورة) والمشاريع القديمة تُعرض كما هي عند غياب `content_blocks`.
- قبل تطبيق الـ migration يعرض المحرر رسالة واضحة بدل الفشل الصامت.

## التطبيق
1. راجع الملف.
2. شغّله مرة واحدة فقط (أوامر `ADD CONSTRAINT` غير idempotent).
3. للتراجع: انظر تعليقات Rollback أسفل الملف.

## الاختبارات
- فحص جاف داخل transaction مع rollback: 18/18 نجحت، والقاعدة بقيت دون تغيير.
- اختبارات الواجهة (Playwright مع Supabase وهمي يحاكي RLS): 63 للمحرر + 52 للموقع.
- **غير مُختبر فعليًا**: التشغيل على Supabase الحقيقي من متصفح، رفع ملفات حقيقي، Google OAuth، SMTP.
