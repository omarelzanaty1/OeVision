# Website Editor – ما يلزم في قاعدة البيانات

> الحالة: **لم تُطبَّق**. الملف جاهز للمراجعة فقط: `supabase/migrations/20261117_website_editor.sql`

## الفكرة
- ثلاثة جداول جديدة + bucket خاص جديد، بدون أي تعديل على جداول/سياسات/Auth/Storage الحالية:
  - `site_content_drafts` — للمدير فقط (قراءة وكتابة). الزوار والعملاء لا يرون المسودات.
  - `site_content_published` — قراءة للجميع، كتابة للمدير فقط.
  - `site_content_versions` — سجل إصدارات للمدير فقط، **إضافة فقط** (لا UPDATE ولا DELETE). تُحفظ نسخة من المنشور قبل كل نشر وقبل إلغاء النشر.
  - bucket خاص `site-drafts` (للمدير فقط): صور المسودات تُرفع هنا ولا يستطيع الزوار قراءتها. عند «نشر» تُنسخ إلى `project-images/site/` (العام) وتُستبدل المراجع بروابط عامة. الإضافة الوحيدة على Storage: الـ bucket الجديد + 3 سياسات تخص `bucket_id='site-drafts'` فقط.
- مفتاح الصفحة: `home | work | brief | contact | global` (global = البانر/الشعار/الصورة الشخصية + روابط التواصل).
- المحتوى JSON: `{"sections":[{id,type,hidden,data}]}`. النشر = نسخ المسودة إلى جدول المنشور.
- الصلاحية عبر `public.is_admin()` نفسها المستخدمة في `projects`.
- قيود: ≤60 قسم، ≤900KB، أنواع أقسام معروفة فقط، مفاتيح صفحات محددة.
- الصور المنشورة تعيش في الـ bucket الحالي `project-images` تحت `site/` (سياساته لم تتغير). (SVG غير مسموح في الـ bucket الحالي؛ الشعار الأصلي SVG يبقى كملف في الموقع ويمكن استبداله بـ PNG/WebP.)

## التوافق
- الموقع يعمل بدون هذه الجداول (محتوى افتراضي مطابق للموقع الحالي)، والمحرر يعرض رسالة واضحة إن لم تُطبَّق.
- لا يُنشأ أي محتوى مخترع: الخبرات/المهارات/التعليم فارغة وتُخفى تلقائيًا، وBehance فارغ حتى تُدخله.

## الاختبارات
- فحص الـ SQL على PostgreSQL 16 محلي مؤقت (أدوار anon/authenticated وstorage تجريبية، لا علاقة له بـ Supabase الفعلي): القيود وRLS تعمل كما هو متوقع (مدير: كتابة؛ عميل: لا قراءة مسودات ولا كتابة؛ زائر: قراءة المنشور فقط؛ سجل الإصدارات إضافة فقط؛ bucket المسودات للمدير فقط).
- **تجربة Dry-run على Supabase الحقيقي** (Transaction واحدة ثم ROLLBACK كامل، 61 من 62 نجحت): الجداول والـ RLS والسياسات والصلاحيات والـ bucket والقيود وخصوصية صور المسودات (مدير/عميل/زائر). لم يبقَ أي أثر بعدها وبقيت بيانات `projects` مطابقة.
- **اختبار A22 (حذف ملفات `site-drafts` بـ SQL) فشل ولم يُثبت أن سياسة الحذف غير موجودة**: Supabase تمنع أي حذف مباشر من جداول storage عبر SQL ("Direct deletion from storage tables is not allowed. Use the Storage API instead")، فالمنع هنا من المنصة لا من غياب السياسة. الإثبات الفعلي يحتاج اختبارًا عبر Storage API من المتصفح.
- اختبارات الواجهة (Playwright + Supabase وهمي): 69 للمحرر، و52/63/63 للموقع/الأدمن/المنشئ.
- **غير مُختبر فعليًا**: Supabase الحقيقي من متصفح، رفع فعلي للتخزين، Google OAuth، SMTP.
- **لا حذف تلقائي** لأي صورة (مسودة أو منشورة) ولا لأي إصدار قديم — لأنها قد تكون مرجعًا في إصدار سابق.
- روابط معاينة المسودات في المحرر (Signed URLs) صالحة ساعة واحدة؛ يكفي إعادة فتح المحرر للتجديد.

## التراجع (من الواجهة)
- **استعادة آخر نسخة منشورة**: تُرجع المحرر لآخر منشور (غير محفوظ حتى تحفظ).
- **الإصدارات السابقة**: قائمة بالنسخ المحفوظة قبل كل نشر؛ «استعادة في المسودة» لا تغيّر الموقع قبل النشر.
- **إلغاء النشر**: يحذف صف الصفحة من `site_content_published` بعد حفظ نسخة منه فيعود الموقع للمحتوى الافتراضي. المسودة تبقى. لا يلمس `projects` ولا أي صورة.

## التراجع
انظر تعليقات Rollback أسفل ملف الـ migration (لا يمس `projects`).
